# v0.3：直接审图、提交返修与统一人物

## 审稿人的操作

1. 先看排在前面的角色基准卡：女主、医生、朋友手袖、检验手袖。通过的基准定义后续人物身份；不满意就填写修改意见。
2. 在每张图下面选择“通过”或“不通过”，写具体评论。点图片仍可放大、比较候选和查看来源。评论与选择在提交前是草稿。
3. 点击“提交意见并生成返修图”。通过只保存人工审核；不通过会保存意见，并为该目标创建一个返修任务。新图返回后继续审核，旧候选保留。

不需要下载、传递、重新导入意见文件。后台未配置、角色基准未通过、目标受理不明或供应商政策拒绝时，意见仍保存并显示等待原因，不伪造排队。每次新的付费生成来自一次明确的审核提交或生成按钮，不自动反复出图直到满意。

## 一致性控制

一个角色有一个身份基准资产，并声明外观和允许的服装状态。每镜明确允许哪些人出现，以及露出正脸、身体、肩背还是仅手部；无人场景明确为空。身份参考强制排在实际上传的参考图前面，不允许在界面取消。场景或上一镜里的偶然人物不能成为身份来源。

基准先经人工通过，再生成依赖镜头。更换基准后，使用旧身份条件的结果必须重新核对。已有50张图片标记为旧版候选，保留真实来源和父图哈希，不冒称为本次新规则的输出。约束能减少漂移；是否面貌、发型、手部和服装真正一致仍须审核生成结果。

## 在线与离线

在线页由同一套组件提供。匿名访客可以看图，只有登录审核的人能保存决定并触发生图。管理员凭据放服务端，不能放分享链接或浏览器代码。

部署时配置：

```dotenv
STORYFLOW_PUBLIC_REVIEW_PROJECTS=<明确允许公开的工程ID>
STORYFLOW_PUBLIC_REVIEW_API_BASE=/api
IMAGE_BASE_URL=<供应商接口地址>
IMAGE_API_KEY=<只在服务端设置>
IMAGE_MODEL=gpt-image-2
```

`/review/<工程ID>` 是在线页。公开API只提供允许公开的审稿数据、真实图片和有限任务状态，不能下载原始医生照、内部回执或完整工程。空项目清单表示不开放匿名审稿。

导出的静态ZIP保留图片和卡片，可离线查看；没有常驻后台时不能直接生成，页面会明确提示。不要给静态包写入密钥来模拟后台。

## 版本与恢复

意见绑定工程版本、内容哈希、候选ID和图片哈希。冲突时保留评论并要求重新核对，不把旧图意见套给新图。提交幂等；任务先保存意图，再请求供应商。供应商返回不明不重投，已经返回的图片下载失败只恢复下载。

SQLite迁移002保存每次提交。数据库备份保留执行状态；工程ZIP保存脱敏历史作为审计证据，导入不会恢复批准、执行任务或登录会话。字幕、展示候选和实际视频首帧仍分别管理。

## 本轮验收边界

本轮验证系统和方案，不自动重生成现有图片，不启动视频或声音。技术测试、后台发布与真实图片的一致性验收分别记录。生产上线结果以本轮最终交付记录为准。
