# 本体视频方法：可执行契约

本项目把需求展开为带稳定 ID 的实体、关系、素材和镜头。`shared/ontology.ts` 在服务端执行校验和编译；它不请求模型、不执行模型脚本，也不把计划写成已经完成的作品。代码不依赖原项目目录、Windows worker 或云动生产服务。

## 数据如何进入制作

```text
需求／资料
    ↓ 人工编辑或模型展开（均为不可信的 JSON 草稿）
实体＋关系＋证据＋锚图＋镜头＋后期图形
    ↓ validateOntology：错误明示，不静默丢镜头或补造事实
compileOntology
    ├─ 审稿数据、逐项目标哈希、素材缺口
    ├─ 可查看的对象／引用／任务关系图
    ├─ 确定性的逐镜提示词与字幕草案
    └─ 有依赖的制作任务计划
            ↓ 明确确认的版本与实际模型能力检查
       生成 → 人工验收真实产物 → 下镜／后期 → 成片
```

### 实体、关系和锚图

- `Entity` 包括角色、场景、道具、动作和医学事实。属性是文本、有限数值或布尔值；不存在可执行代码字段。虚构人物与故事设定可标 `fictional`，不得伪装成事实来源。
- `Evidence` 保存标题、原文摘录、HTTP(S)来源或资料定位说明。医学事实必须挂证据；结构通过只证明有依据引用，不替代医学内容审稿。
- `Relation` 为一等对象，可表达组成、位置、持有、描绘、依据和生成依赖。`projection` 表示关系适合用同框、先后或脚注表达；编译图中可检查关系两端。`depends_on` 的方向是“后镜 → 所依赖前镜”，任务图的箭头则为“前任务 → 后任务”。
- `Asset` 将网络形态参考与实际制作素材分开。`mustShow/rejectIf` 进入镜头提示词和审核依据；来源、许可、SHA-256可追溯。参考图不能自动填平专属素材缺口。
- `Anchor` 把实体的身份或状态绑定到具体图片。绑定文件由存储层注册，不接受本机绝对路径。起止图必须对应同一实体；未知图片、主体或引用都报错。
- `Shot` 采用整数帧，区间左闭右开。对白与字幕均使用全片绝对帧；编译生成哈希时将对白位置转为镜头内相对帧。源片时长与最终剪辑帧数分开，4秒以上的候选源片可剪到更短镜头。

### 校验行为

`validateOntology(value)` 返回 `{path, code, message, severity}`。未写完的草稿仍可保存和显示；调度器必须在执行前拒绝所有 error。空分镜和已登记但未绑定的参考文件为 warning，素材缺口另列。

检查内容包括：对象 ID 全局唯一、引用存在、医学事实证据、属性类型、合法帧率与偶数输出尺寸、整数帧区间、时间线覆盖/重叠、对白/字幕不越镜、字幕冲突、无循环且向前的镜头依赖、锚图类型、文件内容哈希。总帧数上界为 90000；所有时间仍以工程自己的 24 或 25fps 计算。

`PostProgram` 只接受 `text/rect/circle/arrow` 和有限的坐标、色彩、时间、尺寸字段，拒绝未知元素字段。它用于可信渲染器，没有 `eval` 或任意 shell/JavaScript。编译器不会调用渲染器。

## 编译产物与任务

`compileOntology(ontology)` 返回契约中的 `Compiled`：

- `reviewData` 是同一份可审稿本体，不静默删除非法镜头。
- `issues/gaps` 明确指出错误和实际素材缺口。未生成的底片输出槽可以显示缺口，但不能作为自己的生成输入。
- `graph` 显示实体、证据、素材、锚图、关系、镜头和任务。这里只显示计划，实际进度来自持久任务记录。
- `prompts` 由机位、动作入出状态、实体属性、台词、资产必须项/拒收项和证据边界编译，不把后期字幕混入原片生成提示。
- `tasks` 按拓扑排序，包含逐镜输入快照、时基、参考计划、连续性要求和依赖任务 ID。无凭据时可以完整检查这一 dry-run 计划。

| 镜头路线 | 实际任务计划 | 下镜依赖 |
|---|---|---|
| `seedance` | `video:<shotId>` | 本镜通过验收的 video 产物 |
| `doctor` | `voice:<shotId>` → `lipsync:<shotId>` | 本镜通过验收的 lipsync 产物，不能只等待声音任务 |
| `graphic` | `graphic:<shotId>` | 本镜通过验收的图形产物 |
| 最终合成 | `compose` | 各镜最终产物，不直接依赖医生的 voice 中间产物 |

医生的 `firstAnchorId` 指向上传并审核的医生照片。口型任务引用同一句声音任务，要求同一审核音轨；没有照片或合格声音不能执行。仅口型失败可以复用已经合格的同一句声音，换声音则必须重新驱动。编译计划本身不声称口型已经通过。

每个声明的 `dependencies` 与 `depends_on` 关系都会进入实际任务依赖；后镜需要前镜合格成品，不能只看前镜脚本。`input.continuity` 说明前镜产物 ID、动作状态、匹配方法和验收要求。不同场景的依赖不代表把前镜尾帧直接作为新镜头首图；取尾帧接力须明确选择实际验过的画面。

参考条件必须由提交适配器核实。Seedance当前路线是首帧或纯文字输入；规划了末态锚图并不等于供应商实际收到了尾帧。`referencePlan` 保留这一边界，最终以请求与回执中的实际条件为准。

## 哈希与审核追溯

- `hash(value)` 使用 SHA-256＋按字段名排序的规范 JSON；对象字段插入顺序不影响结果，数组顺序保留语义。
- `Compiled.hash` 对应完整本体修订；用于导出、比对与版本定位。
- `shotHashes[id]` 是**生成输入哈希**：包含镜头生成内容、对白、实体、证据、关系、锚图、素材内容哈希，以及递归的前镜生成哈希。只修改后期字幕或后期图形，不应重跑视频生成。
- `targetHashes[id]` 是**审稿目标哈希**：镜头包含完整镜头文字和关联材料，实体包含依据，素材包含来源/许可。修改字幕仍需重新审该镜文字；依赖镜头只在实际生成内容改变时失效。
- `postHash/targetHashes.post` 包含成片时基、镜头排序/区间、字幕、图形及各镜生成输入哈希。实际选用哪个候选产物与入点由存储/调度层追加绑定；本体编译器不虚构尚不存在的媒体选择。

服务端审核记录同时保存 `targetId + targetHash + status + note`。模型编译不能写入用户通过状态，历史通过也不能自动匹配新的哈希。内容改动影响哪些镜头由哈希依赖自然体现；不相关独立镜头继续保留。

## 可移植 V6 示例

`examples/lupus-v6.json` 来自旧 V6 审稿方案，保留20镜、25fps、1500帧、4句医生与4句女主对白、52个专属素材槽。另加12个可分发的参考图条目，合计64资产。52槽中的20个动态底片是产物槽，已从相应镜头的 `requiredAssetIds` 排除，避免任务依赖自己的输出。

`examples/lupus-v6.assets.json` 的 `files` 条目保存 `assetId/path/sha256/mime/source`。路径相对 examples，只能在 assets 子目录；模板加载器验证哈希、注册项目文件后写入 `fileId`。图片署名、许可证链接与实际用途见 `examples/assets/CREDITS.json`，迁移没有改写图像内容。模板未包含 Pexels礼物图片，仅保留需要制作礼物的专属槽；也没有打包指定医生照片、源资料包或旧模型回执。

模板是待审方案：没有V6新影片、口型验收、实际录音或付费任务。医学图文须复核，女主身份与专属症状仍待绑定。默认后期标签由原方案迁移，不能声称已调用 Opus 制作。源资料、本机路径和旧生产服务不参与运行；跨 Mac 开发仅需源码、依赖安装和可选的个人模型配置。

## 回归检查

`tests/ontology.test.ts`覆盖坏引用/重复ID、依赖循环、帧冲突、医生声音与口型拓扑、生成哈希的影响范围、字幕仅后期失效、素材字节变化与文件位置变化的区别、声明式图形限制、无副作用编译以及V6包的脱敏/结构。
